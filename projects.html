Projects

These projects explore practical questions I keep returning to: how do we make technical systems easier to inspect, debug, and trust while they are being built?

The current work is intentionally small and focused. Each project starts with a concrete workflow, a working interface, and a clear next step rather than a large platform too early.

Training Diagnostics

ML Run Doctor

ML Run Doctor helps answer a familiar question after an experiment fails: what went wrong with this training run?

The app accepts one or more training-log CSV files, detects common metric columns, plots normalized trends, compares experiments, and points out likely problems such as overfitting, unstable loss, divergence, or slow convergence. It also suggests basic hyperparameter changes and ranks configuration columns by their relationship with final validation performance.

Status
Working MVP
Built with
React, Next.js, FastAPI, browser-based plots, in-memory analysis
Good for
Reviewing experiment logs, comparing runs, and turning training curves into a short diagnosis

Image Forensics

Forensic Energy Map

Forensic Energy Map is a research baseline for inspecting low-level visual traces in synthetic images.

Instead of returning only a single real-or-synthetic score, the project predicts a spatial energy map that shows where suspicious low-level signal is concentrated. The map is meant to help inspect what a detector is responding to, such as texture, edges, compression, resampling artifacts, or frequency patterns. It also produces an image-level synthetic probability.

The README is careful about the limits of this work: the map is a model response, not proof that a region was generated or edited. That caution is important for forensic tools, where the output needs to support careful review rather than overclaim certainty.

Status
Research baseline
Built with

Good for
Studying synthetic-image traces, detector behavior, and localized forensic signals

Distributed Training

DistViz: Distributed Training Visualizer

DistViz explains why a distributed training step is slow by showing where time goes across workers.

The prototype shows per-rank compute, communication, and idle time; GPU utilization by worker; network bandwidth; pipeline bubbles; worker imbalance; simulated memory fragmentation; and generated bottleneck findings. The current version uses synthetic trace data so the interface and analysis contract can be tested before connecting it to real profiler output.

Status
Prototype with synthetic profiler data
Built with
Next.js, generated trace data, timeline and utilization views
Good for
Explaining stragglers, communication stalls, pipeline bubbles, and uneven worker behavior

Web Security

Polaris

Polaris is an older web security project focused on reducing cross-site scripting risk in PHP applications.

The idea is straightforward: instead of asking every developer to manually handle every unsafe input pattern, Polaris takes a PHP file and produces a more defensive version with input sanitization added. The goal is to move some of the burden of XSS prevention into tooling that can support developers earlier in the workflow.

Status
Archived student/research project
Built with

Good for
Showing early security interests around safer defaults, developer tools, and web application hardening

Project Direction

Together, these projects point toward a consistent theme: tools that make hidden behavior visible. Some focus on model training, one focuses on visual forensic signal, and one comes from web security. The shared goal is to make failure modes and risks visible enough that a researcher or engineer can decide what to try next.
